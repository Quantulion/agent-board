# agent-board, план 4: интеграции — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ревью по кнопке (crit или без инструмента) с раундами и правками агента, одобрение и «Отправить в ревью» командой проекта, заведение задач в трекере (Jira, GitHub Issues) и фоновое чтение их статусов — всё с доски.

**Architecture:** Три адаптера с узкими интерфейсами: `review.py` (crit / none), `ship.py` (команда проекта по шаблону), `tracker.py` (Jira / GitHub / none). Раннер владеет процессами ревью и отправки так же, как ходами агентов (по порядку событий, с восстановлением после перезапуска). Фоновый поток синхронизации трекера переводит задачи от актора `tracker`. UI получает действия в шапке карточки, вкладку «Ревью», массовую отправку, индикатор синхронизации и заведение задач на стадии `tracker`.

**Tech Stack:** Python 3.9 stdlib (`urllib`, `subprocess`, `threading`), `crit` CLI (1.8.x: `crit --no-open` блокируется до «Finish Review», в stderr `approved: true|false`, повторный запуск начинает следующий раунд, `crit comments --json`, `crit comment --reply-to`), vanilla JS. Тесты — pytest с поддельными HTTP-серверами трекеров и поддельным `crit`, node, puppeteer.

**Spec:** `docs/superpowers/specs/2026-11-04-agent-board-design.md` (разделы «Ревью», «Отправка в ревью и закрытие», «Трекер», «Фоновое чтение статусов из трекера», «Адаптеры»); хвосты — `docs/superpowers/plans/2026-11-05-roadmap.md`.

## Global Constraints

- Ничего не пушится и ничего не пишется в трекер без явного действия пользователя: отправка в ревью — кнопкой (команда проекта), заведение задач в трекере — кнопкой на стадии `tracker`; статусы в трекер по умолчанию не пишутся.
- Секреты трекеров (токены, cookie) — только из переменных окружения или файлов, указанных в конфиге по имени/пути; никогда не сохраняются в `project.json`, не попадают в снимок, события, логи и сообщения об ошибках.
- Одобрение (`approved`) ставит только пользователь — кнопкой на доске или завершением раунда crit без комментариев.
- Команда отправки выполняется в worktree задачи, шаблон подставляет только экранированные значения (`shlex.quote`); вывод сохраняется в логи проекта, в карточку — хвост (≤ 4 КБ).
- Фоновая синхронизация трекера: интервал из конфига (по умолчанию 30 с), один поток на сервер, ошибки видны в снимке (`tracker_sync {at, ok, error}`), без бесконечных повторов при 401 (пауза до изменения конфига или ручного «Повторить»).
- Рантайм без новых зависимостей; UI без сборки.

## Review Focus

1. Пользователь завершил раунд crit с комментариями → агент получает именно эти комментарии, правит, отвечает в crit, открывается следующий раунд; завершение без комментариев → задача одобрена и закоммичена (Task 2, Task 7).
2. Сервер перезапустили, пока шёл раунд crit → раунд не теряется: процесс crit найден/перезапущен с `--session`, карточка показывает ту же ссылку (Task 2).
3. Команда отправки упала (ненулевой код) → статус не меняется, в карточке хвост вывода и ошибка, повторная отправка возможна; зависимая задача в цепочке не отправляется раньше зависимости (Task 3).
4. Трекер недоступен / вернул 401 → доска показывает ошибку синхронизации, задачи не переводятся, нет шквала запросов; после исправления синхронизация продолжается (Task 5).
5. Токен трекера ни разу не попадает в ответы API, события, логи, тексты ошибок (Task 4, Task 5).

### Task 2: Ревью — адаптеры, раунды, раннер

**Files:** Create `review.py`, `board/tests/fakes/fake_crit.py`; Modify `board.py`, `runner.py`, `server.py`, `cli.py`, `prompts.py` + `prompts/task_system.md`, `model.py`; Tests `test_review.py`, `test_runner.py`, `test_server.py`, `test_prompts.py`

**Interfaces:**
- `config.review = {"tool": "crit" | "none", "binary": "crit"}`.
- `Task.review = {"round": int, "state": "idle"|"open"|"changes"|"fixing"|"approved", "url": str|None, "session": str|None, "history": [{"round", "state", "comments": int, "at"}]}` — runner-поле (system).
- API `POST /api/p/<slug>/tasks/<key>/review` `{actor: "user"}` → раннер начинает раунд (задача должна быть `in_review`; иначе 400). `POST .../approve` `{actor: "user"}` → переход `approved` от `user` (для `tool: none` и как ручное одобрение при crit).
- `CritReview`: старт раунда — `crit --no-open --base-branch <base_branch> -o <project>/crit` в worktree задачи (фоновый процесс в своей группе), ссылка — из вывода/`crit status --json`; конец раунда — завершение процесса: `approved: true` в stderr или 0 комментариев → `approve` от `user`; иначе `crit comments --json` → агент будится причиной `review` с комментариями (`{round, comments: [{id, path, line, body}]}`); когда агент закончил ход (не в `waiting_answer`) — раннер запускает следующий раунд тем же способом (повторный запуск = следующий раунд). Сессия crit (`--session`) сохраняется в `task.review.session`; при восстановлении после перезапуска — переподключение с `--session`.
- `NoReview`: «Ревью» показывает дифф (вкладка «Изменения»); «Одобрить»/«Вернуть с комментарием» (сообщение в тред + переход `in_progress`).
- Новая причина пробуждения `review`; промпт агента: как отвечать на комментарии (`crit comment --reply-to <id> "<текст>"` в worktree), не завершать раунд самому, по готовности — закончить ход (раннер откроет раунд).
- Исследовать перед кодом (в отчёт): точный вывод `crit --no-open` (где ссылка, где `approved:`), `crit status --json`, `crit comments --json`, поведение `--session`; на основе этого — `fake_crit.py` с тем же интерфейсом для тестов.

- [ ] Тесты (с fake_crit): раунд с комментариями → агент разбужен с ними, после хода — раунд 2; раунд без комментариев → `approved` + коммит; перезапуск сервера во время раунда → переподключение, та же ссылка (Review Focus 2); `tool: none` — одобрение и возврат; ревью не начинается не из `in_review`; повторный клик не запускает второй процесс.
- [ ] Commit `int: ревью`

### Task 3: Отправка в ревью

**Files:** Create `ship.py`; Modify `runner.py`, `server.py`, `board.py`, `config.py`, `cli.py`; Tests `test_ship.py`, `test_runner.py`, `test_server.py`

**Interfaces:**
- `config.ship = {"command": str | None, "timeout": 600}`; плейсхолдеры `{key} {title} {branch} {base} {worktree} {repo}` (значения — `shlex.quote`), запуск `bash -lc <command>` в worktree; `{base}` — ветка зависимости, если она ещё не `done`, иначе базовая ветка репозитория.
- API `POST /api/p/<slug>/ship` `{keys: [..], actor: "user"}` → раннер ставит в очередь отправки; задачи только в `approved`; порядок — топологический: задача не отправляется, пока её незавершённые зависимости в этом же запросе не отправлены успешно или уже `sent`/`done` (иначе ошибка «сначала отправьте <K>»).
- Перед командой раннер коммитит остатки (`commit_all`, если есть изменения после одобрения — сообщение `<KEY> <title>`). Успех → переход `sent` от `system`, `task.ship = {state: "done", at, output_tail}`; ошибка/таймаут → `task.ship = {state: "error", output_tail, exit_code}`, статус не меняется, системное сообщение в тред (Review Focus 3). Полный вывод — `<project>/logs/<KEY>.ship.log`.
- Без `ship.command` кнопка в UI скрыта, API → 400 с понятным текстом.

- [ ] Тесты: шаблон с кавычками/пробелами в названии экранируется; цепочка A→B в одном запросе отправляется по порядку, B с `{base}=A`; ошибка A → B не отправлена; повтор после исправления; таймаут убивает группу процессов; задача не в `approved` → 400.
- [ ] Commit `int: отправка в ревью`

### Task 4: Трекеры — адаптеры и заведение задач

**Files:** Create `tracker.py`, `board/tests/fakes/{fake_jira,fake_github}.py`; Modify `server.py`, `board.py`, `config.py`, `cli.py`; Tests `test_tracker.py`, `test_server.py`

**Interfaces:**
- `config.tracker`:
  - `{"type": "none"}`;
  - `{"type": "jira", "url", "project", "issue_type", "epic": "PROJ-1"|null, "epic_field": "customfield_10007"|null, "components": [..], "labels": [..], "extra_fields": {}, "link_type": "Blocks", "auth": {"type": "token_env", "env": "JIRA_TOKEN", "user_env": "JIRA_USER"} | {"type": "cookie_file", "path": "~/.config/agent-board/jira-cookie.txt"}, "statuses": {"<Jira status name>": "<board status>"}}`;
  - `{"type": "github", "repo": "owner/name", "labels": [..], "auth": {"type": "token_env", "env": "GITHUB_TOKEN"}, "statuses": {"open": null, "closed": "done"}}`.
- `TrackerAdapter`: `create_issue(task) -> {key, url}`, `link(blocker_key, blocked_key)`, `get_statuses(keys) -> {key: status_name}`, `check() -> None` (проверка доступа). Все ошибки — `TrackerError` с текстом без секретов (заголовки и тела запросов не логируются; в тексте ошибки маскируются значения токенов/cookie).
- API `POST /api/p/<slug>/tracker/create` `{actor: "user"}` (стадия `tracker`) → создаёт задачи без `tracker_key` в порядке графа, записывает `tracker_key/url` (update от `system`), затем связи зависимостей; частичный сбой → уже созданные сохранены, ответ со списком ошибок, повтор продолжает с несозданных (идемпотентно). CLI `agent-board tracker create`, `agent-board tracker check`.
- Название задачи в трекере: `title` (шаблон `config.tracker.title_template`, по умолчанию `{title}`), описание: описание + критерий готовности + «Зависит от: …».

- [ ] Тесты с поддельными серверами: создание и связи в Jira (тела запросов, поле эпика, компоненты), в GitHub (тело со ссылками на зависимости); идемпотентный повтор после частичного сбоя; 401 → понятная ошибка без токена (Review Focus 5: токен не встречается ни в ответе API, ни в событиях, ни в логе — проверить поиском по всем файлам проекта); `check`.
- [ ] Commit `int: трекеры и заведение задач`

### Task 5: Фоновая синхронизация статусов

**Files:** Modify `tracker.py` (`TrackerSync`), `server.py` (запуск потока), `board.py` (снимок `tracker_sync`), `runner.py` (реакции уже есть: `tracker`-актор); Tests `test_tracker.py`, `test_server.py`

- [ ] `TrackerSync(server, interval)`: раз в `config.tracker.poll_seconds` (по умолчанию 30) для проектов с трекером на стадиях `work`/`done` читает статусы задач с `tracker_key`, маппит через `statuses`, переводит изменившиеся `transition(..., actor="tracker")` (только если доска не в этом статусе; `done` разблокирует зависимых — уже реализовано; переоткрытие → `in_progress` будит агента — уже реализовано). Событие `tracker_synced {ok, changed: [..], error}`; снимок `tracker_sync {at, ok, error, paused}`.
- [ ] Ошибки: сеть — повтор с паузой до 5 мин; 401/403 — `paused: true` до изменения конфига трекера или API `POST /api/p/<slug>/tracker/sync {actor: "user"}` («Повторить сейчас»). Немаппленные статусы игнорируются (в снимке — список «неизвестных статусов» для подсказки).
- [ ] Тесты: изменение статуса в поддельной Jira → задача `done` и зависимая разблокирована; переоткрытие → агент разбужен; 401 → пауза, без повторных запросов в течение 3 интервалов, «Повторить» снимает паузу (Review Focus 4); интервал соблюдается (поддельные часы).
