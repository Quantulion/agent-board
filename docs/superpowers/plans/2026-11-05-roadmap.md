# agent-board — дорожная карта планов

Спека: `docs/superpowers/specs/2026-11-04-agent-board-design.md`. Макеты: `docs/design/mockups/`.

Спека охватывает несколько подсистем, поэтому реализация разбита на пять планов. Каждый даёт работающий, тестируемый результат; следующий план пишется после завершения предыдущего, опираясь на его фактические интерфейсы.

| # | План | Результат | Зависит от |
|---|---|---|---|
| 1 | Ядро: модель, хранилище, граф, переходы, HTTP API, CLI | Демон доски с API и SSE, консольная утилита; всё состояние и правила переходов покрыты тестами. Агентов ещё нет: реакции сервера выражены событиями | — |
| 2 | Исполнение: адаптеры харнессов (Claude Code, Codex), запуск/продолжение сессий, worktree и цепочки веток, общие ресурсы с арендой, агент проекта, прерванные ходы | Сервер сам запускает агентов на разблокированные задачи, будит их сообщениями, агент проекта отвечает в треде «Проект» | 1 |
| 3 | Интерфейс: перенос утверждённых макетов на живые данные (доска, карточка со вкладками, граф, тред «Проект», «Ждут вас», страница разбивки) | Доска в браузере на реальном API с live-обновлением | 1 (2 — для живых агентов) |
| 4 | Интеграции: трекеры (Jira, GitHub Issues), фоновое чтение статусов, ревью (crit / без инструмента), команда «Отправить в ревью» | Задачи заводятся в трекере, статусы подтягиваются, ревью и отправка работают по кнопкам | 1, 2 |
| 5 | Скилл: SKILL.md, настройка проекта вопросами, вход (план / задачи), разбивка и согласование, платформенные справочники, упаковка плагина | Скилл, который пользователь запускает после любого скилла планирования | 1–4 |

Стек (решение builder'а, спека оставила его открытым): Python ≥ 3.9 только на стандартной библиотеке в рантайме (есть на macOS «из коробки», ставится везде без Node-тулчейна), pytest — только для разработки. UI — статический HTML/CSS/vanilla JS, как в макетах.

## Хвосты плана 1 (взять в план 2)

- **Порт на macOS:** из-за SO_REUSEADDR сервер занимает `127.0.0.1:8737`, даже если другое приложение слушает `0.0.0.0:8737`. Перед bind в цикле портов по умолчанию пропускать порт, на котором уже кто-то отвечает.
- `BoardServer.start()`: действия после bind (поток, запись `server.json`) — внутри try с освобождением блокировки; существующий `<home>/token` приводить к правам 0600.
- `base_for` молча пропускает зависимость в `approved`/`sent` без ветки — раннер должен решать явно (иначе worktree без кода зависимости); дедуп веток.
- Ребейз зависимых задач при изменении ветки зависимости (реопен, вливание) — реакция раннера.
- Исключение в `on_event` обрывает операцию Board на середине — подписчики раннера не должны бросать.
- `ask` на `done`/`sent`/`cancelled` переоткрывает задачу; повтор перехода в тот же статус порождает событие.
- Актор самоназванный (`AGENT_BOARD_ACTOR`): выдавать агентам токены, привязанные к актору и задаче.
- План 3: после установки cookie по `/?token=` делать редирект на `/`, чтобы токен не оставался в адресной строке.
- В тексте плана 1 сигнатура `update_task(key, actor, **fields)` устарела: теперь `update_task(key, actor, fields: dict)`.

## Хвосты плана 2 (взять в план 3)

- **Перенос работы при ребейзе:** если восстановление незакоммиченной работы из `refs/agent-board/<KEY>/carry` падает на неотслеживаемых файлах, git уже применил отслеживаемые изменения — дерево остаётся наполовину восстановленным. Нужно: при сбое `reset --hard` + `clean -fd` до ребейзнутого HEAD (вся работа остаётся в ref), тест проверяет чистоту дерева.
- Задача в `approved` не должна получать новые ходы по накопленным причинам (гейт по статусу в `_run_task`; сообщения пользователю в одобренной задаче — показывать, но агент не будится без возврата в работу).
- Актор в HTTP самоназванный, токен общий: защита P14/P19 от ошибок, не от враждебного агента — токены на агента/задачу.
- Codex: не проверен вживую (запуск, resume, sandbox и сеть, формат потока); id сессии — разбирать `thread.started` во время потока.
- Таймаут хода; источник общего лимита агентов на сервер; счётчик неудач и счётчик переписки агентов — в памяти; фоновые процессы агента после хода не добиваются.
- Правки правил в конфиге не доходят до уже начатой сессии Claude (системный промпт первого хода сохраняется при resume).
- Если join рабочего потока раннера при остановке превышает 30 с, он может начать ход после прохода остановки.

## Хвосты плана 3 (взять в план 4)

- В начале плана 4 разнести `board.js`/`card.js` (≈770–790 строк): `status.js` (меню статуса, перенос, диалог внешнего блокера), `header.js` (степпер, индикатор соединения), `chips.js` (общие чипы статусов); в шапке карточки — точка расширения для действий вместо статичных неактивных кнопок «Ревью»/«Отправить в ревью».
- Вкладка «Ревью» и бейдж раунда на карточке, фильтр «волна» — вместе с ревью и волнами; формат `task.review {round, state, history, url}` пока предварительный.
- Индикатор синхронизации с трекером в шапке; при подключённом трекере переход decomposition→work не виден в снимке — нужна история стадий.
- Серверная операция «добавить зависимость» вместо полной замены deps (поле «Блокирует» в новой задаче делает read-then-write).
- Доступность: focus trap и `aria-modal` у панели и модалок, клавиатурный ресайз, стрелки в меню статуса, `aria-controls` у вкладок, двойное объявление ошибок в тостах.
- Тред перечитывается целиком на каждое сообщение; дифф целиком читается в память до обрезки; `/projects` грузит `/state` на каждый проект.
- Шапка на 1440 px может переноситься, если одновременно видны «Трекер пропущен», чип предложений и «Завершить проект».
- Модалка новой задачи закрывается по Esc/клику без подтверждения — длинное описание теряется.

## Хвосты плана 4 (взять в план 5)

- Проверка конфига: проверки файловой системы и `git rev-parse` по репозиториям — вне блокировки доски и только для изменившихся репозиториев; полные проверки — для изменённых полей, структурные — для итогового конфига (иначе старые проекты, сохранённые до строгих проверок, не дают править настройки).
- `config set` с именем поля вроде `to_dict` даёт 500 вместо 400 — сверять с полями dataclass.
- Агент задачи может завести задачу через `add-task` (актор `agent` допускается) — решить: только через предложения агента проекта или оставить.
- Синхронизация трекера опрашивает проекты в `done` бесконечно; проекты синхронизируются последовательно (один зависший задерживает остальные).
- `Bash(crit comment:*)` разрешает агенту и `--resolve` — запрещено только промптом.
- Устаревший ключ `ship_command` молча теряется; данные ревью crit не чистятся после отмены, лог ревью растёт.
- Проверить на своей Jira: направление связи «A blocks B» и поведение просроченной cookie (ожидается пауза синхронизации).
