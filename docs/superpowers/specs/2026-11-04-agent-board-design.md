# agent-board — дизайн

Дата: 2026-11-04. Статус: черновик на согласование.

## Зачем

Автор прошёл большой эпик (вынос таблиц из монолита в микросервис, ~19 задач в нескольких репозиториях) в таком режиме: сначала план, потом доска с карточками задач, на каждую незаблокированную задачу — свой агент в своём git worktree, вопросы и обсуждение — в карточке, ревью — в crit, отправка в ревью — по кнопке. Подход подтвердил себя на практике. Ценное в нём:

- доска — главный интерфейс: в терминал почти не нужно возвращаться;
- у каждой задачи свой агент со своим контекстом, вопросы задаются в рамках задачи, диалог сохраняется и к нему можно вернуться;
- контекст корневого агента не засоряется частностями задач, но с ним можно обсудить проект целиком;
- видно, что и почему заблокировано, на каком этапе проект, что сделано и что в работе;
- независимые задачи идут параллельно;
- все артефакты планирования доступны с доски.

Тогда это было собрано вручную под один эпик. `agent-board` — переиспользуемый скилл с этим процессом, который можно выложить на GitHub для всех, включая пользователей Codex и других агентов.

## Что было не так в прошлый раз (должно уйти)

1. Все сообщения из карточек шли через корневого агента: засорялся его контекст, он забывал переводить статусы («почему задача всё ещё в Ждёт ответа?»).
2. Каждый день нужно было просить агента переподключиться к доске по ссылке: после переподключения сессия не получала события.
3. Зависимости и блокеры велись вручную: не было авторазблокировки, висели устаревшие и ложные блокеры.
4. Агенты «подвисали» в очереди на общий ресурс (лок функтестов), а на доске этого не было видно.
5. Декомпозиция нарушала правило проекта («одна задача — один деплой одного сервиса»), и это всплывало поздно.
6. Отчёты лежали во временной папке и пропали при её очистке.
7. Вопросы без контекста были непонятны; пришлось добавлять раскрывающийся «Контекст».
8. Двигать статус задачи можно было только попросив агента.

## Цели

- Принять на вход план от любого скилла планирования (или просто текст) либо готовый список задач.
- Разбить план на задачи, построить граф зависимостей, согласовать разбивку с пользователем на отдельной HTML-странице.
- Опционально завести задачи во внешнем трекере.
- Поднять локальную доску и вести на ней всю работу: агенты задач, вопросы, обсуждение, ревью, отправка в ревью.
- Сохранять всё состояние (включая контексты агентов) между перезапусками.
- Работать в Claude Code и Codex; другие харнессы — через адаптер.

## Не цели

- Не писать статусы в трекер автоматически. Только по явной просьбе. Чтение статусов из трекера — автоматическое (см. 3а).
- Не коммитить и не пушить без явного действия пользователя.
- Не заменять скиллы планирования: скилл начинается там, где план уже есть.
- Не делать облачный/многопользовательский сервис. Доска локальная, для одного человека.
- Артефакт claude.ai — не основной носитель. Только по просьбе пользователя (например, снимок, чтобы поделиться).

## Основные решения (приняты с пользователем)

1. **Доска — локальный веб-сервер** (localhost), открывается в браузере. Не зависит от аккаунта и харнесса.
2. **Агентами управляет сервер доски**, а не терминальная сессия. Каждый агент — сохранённая сессия CLI в фоновом режиме (Claude: `claude -p --session-id <uuid>` при старте, `claude -p --resume <id>` для продолжения, `--output-format stream-json`). Сообщение в карточке → сервер продолжает сессию агента этим сообщением → ответ появляется в треде.
3. **Контекст агентов переживает перезапуски** сервера, терминала, машины: id сессии хранится в карточке.
4. **Агент проекта** — отдельная сохранённая сессия с контекстом всего проекта, свой тред «Проект» на доске. Для общих и архитектурных вопросов.
5. **Разговор с агентом задачи — в карточке**, с сохранённой историей. Отдельные вкладки терминала на агентов — нет.
6. **Новую задачу можно создать с доски** (в т.ч. исследование), агент на неё запускается сам.
7. **Статусы двигаются кнопкой/перетаскиванием**, как в Jira, без сообщения агенту.
8. **Трекер: заводим задачи и в фоне читаем статусы** (трекер → доска, по умолчанию раз в 30 с). В трекер статусы по умолчанию не пишем.
9. **Ревью по умолчанию — crit**, но при настройке скилл проверяет, установлен ли он, и предлагает альтернативу.
10. **Два входа:** план (разбиваем) или готовые задачи (не разбиваем, только достраиваем зависимости).
11. **Разбивка согласуется на отдельной HTML-странице** с графом; после согласования она становится ссылкой на доске.
12. Публикация на GitHub, ядро без специфики конкретной компании.

## Процесс

### 0. Настройка проекта

При первом запуске в проекте скилл короткими вопросами собирает файл настроек проекта (см. «Настройки»). Повторные запуски его переиспользуют. Проект может охватывать несколько репозиториев.

### 1. Вход

- **План**: путь к файлу плана/спеки, ссылки на документы, или текст. Скилл разбивает на задачи.
- **Готовые задачи**: список, таблица, ключи эпика в трекере. Скилл не разбивает, только достраивает недостающие зависимости и поля.

### 2. Разбивка и согласование

Скилл (в терминальной сессии) строит список задач и граф и публикует страницу разбивки на том же локальном сервере:

- задачи: заголовок, что сделать, критерий готовности, репозиторий/сервис, тип (код / исследование), оценка, зависимости;
- граф зависимостей визуально, с критическим путём и параллельными ветками;
- проверка правил декомпозиции из настроек; нарушения подсвечены;
- ссылки на исходный план и документы.

Пользователь комментирует задачи на странице и в общем треде; скилл переделывает, пока пользователь не утвердит. До утверждения ничего не заводится.

### 3. Трекер (опционально)

После утверждения скилл заводит задачи через адаптер трекера, проставляет связи, записывает ключи в карточки. Ключ трекера становится видимым кодом задачи (если трекера нет — короткий код вида `T1`).

### 3а. Фоновое чтение статусов из трекера

Если трекер настроен, сервер в фоне раз в N секунд (по умолчанию 30, настраивается) читает статусы задач из трекера и обновляет доску. Направление только трекер → доска; в трекер сервер по-прежнему ничего не пишет без просьбы.

- Соответствие статусов трекера статусам доски задаётся в настройках (например, Jira «Closed»/«Deployed» → «Готово», «Reopened» → «В работе»).
- Задача дошла до готовности в трекере → карточка в «Готово» → зависимые задачи разблокируются, на них стартуют агенты. Так задачи не застревают в «Отправлена» до ручного уведомления.
- Задачу переоткрыли в трекере → карточка возвращается в «В работе», агент будится с пометкой, что задачу переоткрыли в трекере.
- Каждое такое изменение попадает в журнал событий с пометкой «из трекера»; в карточке видно время последней синхронизации и ошибки доступа к трекеру (протухла авторизация и т.п.), а не молчаливое отставание.

### 4. Доска

Скилл запускает сервер доски в фоне и даёт ссылку. Создаётся агент проекта (см. ниже). Сервер запускает агентов на все задачи без открытых зависимостей, с учётом лимита параллельности.

Терминал дальше молчит. Опционально в него приходят короткие строки о ключевых событиях («T12 ждёт ответа», «T15 разблокирована, агент запущен»).

Возврат после закрытия сессии: «подними доску проекта X» → сервер стартует из сохранённого состояния. Переподключаться к доске по ссылке не нужно никогда.

### 5. Работа над задачей

- Сервер создаёт worktree задачи в нужном репозитории (ветка по шаблону из настроек, от базовой ветки), запускает агента с промптом задачи.
- Агент работает в своём worktree, сам ведёт свою карточку через консольную утилиту доски: статус, краткое резюме, todo, изменённые файлы, найденное, вопросы.
- Вопрос пользователю: агент не ждёт. Кладёт вопрос в карточку (текст, варианты, раскрывающийся контекст для человека без знания предметки, рекомендация), ставит «Ждёт ответа» и продолжает то, что не зависит от ответа, либо завершает ход.
- Ответ или сообщение пользователя в треде карточки → сервер продолжает сессию агента. Агент отвечает в тред сам и сам возвращает статус.
- Вопрос, затрагивающий систему целиком, агент задачи эскалирует агенту проекта.
- Общие ресурсы (см. «Настройки»): агент берёт их через очередь сервера; пока ждёт — карточка показывает «ждёт очереди: <ресурс>».

### 6. Ревью

- Кнопка «Ревью» в карточке → агент задачи запускает интерактивное ревью инструментом из настроек (по умолчанию crit), ставит «На ревью» со ссылкой на сессию ревью.
- После завершения ревью пользователем агент вносит правки, отвечает на комментарии, гоняет проверки и открывает следующий раунд, пока пользователь не одобрит.
- Номер раунда и короткая история раундов видны в карточке.
- Независимо от инструмента в карточке всегда доступен дифф worktree относительно базовой ветки и список изменённых файлов.

### 7. Отправка в ревью и закрытие

- Кнопка «Отправить в ревью» доступна только для одобренных задач; можно выбрать несколько. Выполняет команду из настроек (коммит/пуш/PR/перевод в трекере — как настроит пользователь). Без этой кнопки никто не коммитит и не пушит.
- Worktree не удаляется автоматически (на случай реопена). Удаление — отдельным действием.

## Агенты

### Агент задачи

- Одна сохранённая сессия на задачу, id в карточке. Засыпает после хода, будится сообщением в треде, ответом на вопрос, ручным переводом статуса, запросом ревью.
- Промпт задачи собирается из: описания и критерия готовности, контекста проекта (краткий бриф + ссылки на документы), правил проекта (worktree строго, не коммитить, не трогать чужое, как гонять тесты, какие скиллы грузить), инструкции по работе с доской (утилита, формат вопросов, эскалация).
- Тип «исследование»: без worktree-кода, результат — отчёт (файл в хранилище проекта), ссылка в карточке; ревью/отправка не нужны, задача закрывается пользователем.
- Кнопка «Открыть в терминале» копирует команду продолжения сессии агента в его worktree — запасной выход, чтобы поговорить вживую.

### Агент проекта

- Сохранённая сессия с контекстом проекта: планирование, решения, граф, ссылки на артефакты.
- Свой тред «Проект» на доске.
- В курсе без раздувания: сервер ведёт журнал значимых событий; при каждом обращении агент проекта получает сводку изменений с прошлого раза, детали читает сам утилитой (карточка, тред, дифф).
- Может: писать агентам задач (сообщение видно в треде карточки с пометкой автора), принимать эскалации и при необходимости выносить вопрос пользователю; предлагать новые задачи и изменения зависимостей — применяются только после подтверждения пользователем кнопкой.
- Комментарии к странице разбивки после её утверждения тоже идут ему.

## Статусы и переходы

Статусы: Не начата, Заблокирована, В работе, Ждёт ответа, Ждёт очереди, На ревью, Одобрена, Отправлена, Готово, Отменена.

- «Заблокирована» вычисляется из зависимостей (с видимой причиной: какими задачами), плюс можно поставить вручную внешний блокер с текстом причины.
- Пользователь двигает любую карточку вручную. Переходы запускают реакции сервера:
  - в «Одобрена» (с цепочками веток) или «Готово» (без цепочек) → зависимые задачи разблокируются, на них стартуют агенты (см. «Зависимые задачи и ветки»);
  - обратно в «В работе» → будится агент с пометкой, откуда вернули;
  - в «Отменена» → агент останавливается, задача удаляется из зависимостей остальных (с записью в журнал).
- Агент сам ставит «В работе», «Ждёт ответа», «На ревью», «Одобрена» (по факту одобрения в ревью).

## Доска (что видит пользователь)

- Колонки по статусам, сводка по количеству, фильтры (репозиторий/сервис, волна, тип), бейджи: открытые вопросы, непрочитанные сообщения, состояние ревью, ожидание очереди.
- Индикатор этапа проекта (разбивка → трекер → работа → завершение) и прогресс.
- Блок ссылок: план, документы планирования, страница разбивки, отчёты исследований.
- Вид графа зависимостей с текущими статусами.
- Карточка: описание, критерий готовности, зависимости и почему заблокирована, worktree/ветка, ключ и ссылка трекера, резюме и todo агента, вопросы с вариантами и «Контекстом», тред, ревью (раунды, ссылка), дифф и изменённые файлы, кнопки (ревью, отправить, перевести статус, открыть в терминале).
- Кнопка «Новая задача»: описание, тип, зависимости/блокирует.
- Тред «Проект».
- Live-обновление без перезагрузки.

### Утверждённый дизайн

Эталон интерфейса — кликабельные макеты в `docs/design/mockups/` (`board.html`, `card.html`, `decomposition.html`, обзор и ключевые решения — в `index.html`). Реализация повторяет их по структуре, поведению и визуальному языку.

- Чистый HTML/CSS/vanilla JS без UI-библиотек и сборки (вариант на дизайн-системе Astryx рассмотрен и отклонён: требует React и сборки, а доска должна ставиться у всех без Node-тулчейна).
- Полоса «Ждут вас» под шапкой — всё, что требует действия пользователя.
- Перенос карточки показывает реакцию сервера (кого разблокировало, кого разбудили) с возможностью отменить.
- Тред «Проект» — постоянная боковая панель.
- Карточка задачи — выезжающая панель с ресайзом и вкладками «Обзор / Тред / Ревью / Изменения» со счётчиками; у исследований — только «Обзор / Тред». Смена вкладки меняет только её содержимое, без перерисовки панели и повторной анимации.
- Узлы графа никогда не переполняются: статус в одну строку, заголовок до двух строк с обрезкой.
- Чипы и счётчики — всегда по размеру содержимого.
- Светлая и тёмная темы, переключатель.

## Настройки проекта

Файл настроек проекта (формат — на усмотрение builder'а), собирается вопросами при первом запуске:

- репозитории проекта и базовые ветки; шаблон имени ветки/worktree;
- харнесс агентов и режим разрешений для фоновых сессий (интерактивно одобрять в фоне нельзя — пользователь должен выбрать осознанно);
- лимит параллельных агентов;
- трекер: нет / Jira / GitHub Issues / Linear + его параметры (проект, эпик, поля, компонент и т.п.), интервал фонового чтения статусов и соответствие статусов трекера статусам доски;
- правила декомпозиции (текстом; скилл проверяет их на странице разбивки);
- инструмент ревью: crit / другой (команда или скилл) / нет;
- команда «отправить в ревью»;
- общие ресурсы с эксклюзивным доступом (например, функциональные тесты, локальный стенд) и как их использовать;
- правила для агентов: ссылки на CLAUDE.md/AGENTS.md, скиллы, которые грузить, команды сборки и тестов;
- язык интерфейса и общения (по умолчанию — язык пользователя).

## Хранение

Всё состояние — не во временной папке, а в постоянном каталоге проекта (предложение: `~/.agent-board/projects/<slug>/`, т.к. проект может охватывать несколько репозиториев): задачи, треды, вопросы, журнал событий, отчёты, страница разбивки, id сессий агентов. Worktree — внутри соответствующих репозиториев (с исключением из git).

## Адаптеры

- **Харнесс**: запуск сессии с заданным id/промптом/cwd, продолжение сессии сообщением, остановка, чтение потока вывода, команда «открыть в терминале». v1: Claude Code и Codex.
- **Трекер**: завести задачу, связать задачи, прочитать статус, (по просьбе) перевести статус. v1: нет трекера, Jira, GitHub Issues; Linear — если не дорого.
- **Ревью**: запустить сессию ревью, понять, что пользователь завершил раунд, прочитать комментарии, ответить. v1: crit, «без инструмента» (только дифф на доске).

## Ограничения

- Работает без claude.ai и без особых возможностей аккаунта.
- Ни одно действие, публикующее код или меняющее трекер, не выполняется без явного действия пользователя.
- Тексты скилла — на английском (публичный репозиторий); интерфейс и общение — на языке пользователя.

## Решения, принятые мной (не пользователем) — проверить

- Название `agent-board`, репозиторий `~/code/CianProjects/agent-board`.
- Ревью ведёт сам агент задачи, а не отдельный исполнитель (у него уже есть контекст).
- Тип задачи «исследование» с отчётом вместо кода.
- Страница разбивки и доска — один сервер, общий механизм комментариев.
- Хранилище в `~/.agent-board/projects/<slug>/`.
- Опциональные уведомления в терминал.

### Зависимые задачи и ветки (решение пользователя)

По умолчанию разрешены **цепочки веток**; настройкой проекта их можно выключить.

- С цепочками: зависимая задача разблокируется, когда ревью зависимости одобрено («Одобрена»), и её worktree создаётся от ветки зависимости. Если незалитых зависимостей несколько — от базовой ветки с влитыми ветками зависимостей (моё решение).
- Когда ветка зависимости меняется (правки после реопена) или зависимость вливается в базовую ветку, агент зависимой задачи будится и перебазирует свою ветку. Конфликты он решает сам; если не может — вопрос в карточке.
- «Отправить в ревью» для задачи в цепочке учитывает порядок: нельзя отправить зависимую задачу раньше её зависимостей (или команда отправки получает базу для PR — ветку зависимости; детали — builder'у).
- Без цепочек: зависимая задача разблокируется, только когда зависимость в «Готово» (в т.ч. по фоновому чтению трекера), worktree — от свежей базовой ветки.

### Самостоятельность агента проекта (решение пользователя)

- Отвечать агентам задач на эскалации и писать им может сам.
- Новые задачи, изменения зависимостей, отмену задач — только **предлагает**: предложение появляется на доске (в треде «Проект» и в затронутых карточках) с кнопками «Применить» / «Отклонить». Граф меняется только после подтверждения пользователем.

### Решения по вопросам builder-check (мои)

- **Разбивку ведёт агент проекта.** Терминальная сессия только собирает вход (план/задачи, настройки) и передаёт их серверу; сервер создаёт агента проекта до разбивки, и цикл согласования (комментарии на странице разбивки → правки) идёт через него. Терминалу не нужно получать события со страницы — это важно для Codex, где нет аналога Monitor. Уведомления в терминал остаются опцией.
- **Сервер — один демон на все проекты**, живёт независимо от терминала, один порт. Несколько проектов одновременно поддерживаются; лимит параллельных агентов — на проект плюс общий верхний.
- **Прерванный ход** (сервер остановился, машина уснула посреди хода): при старте сервер помечает карточку «ход прерван» и продолжает сессию агента сообщением о прерывании; пользователь видит это в треде.
- **Общие ресурсы:** агент сам получает эксклюзивную блокировку через утилиту доски (блокирующий вызов, ожидание видно на карточке как «ждёт очереди») и сам выполняет работу. Блокировка — с арендой: освобождается при завершении процесса агента или по таймауту, чтобы упавший агент не держал ресурс.

### Справочные материалы прошлого опыта

Ссылки на прошлую доску, промпты агентов и формат вопросов — в локальном файле `docs/local-prior-art.md` (не в git: содержит внутренние данные). Это ориентир по UX и формату вопросов; код пишется заново (другая архитектура: локальный сервер вместо артефакта с БД).
